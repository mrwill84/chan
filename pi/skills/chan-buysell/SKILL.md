# 缠论买卖点研判

## 第一条规矩：你不划线

划线是确定性几何算法——包含关系、分型、笔、线段的特征序列、中枢的 ZG/ZD、
MACD 面积背驰。它已经实现成 Python 引擎，有近 300 条测试和一套原文不变量断言
压着，还有一个多空镜像自检（把行情上下翻转，每个买点必须变成同位置的卖点）。

**所以：先调 `chan_analyze`，绝对不要自己数K线画笔。**

你自己从K线推出来的笔和中枢几乎一定和引擎不一致，而一旦不一致，后面所有
「这是三买」的话都是错的。你的活是**读引擎的输出做研判、给人话理由**，
不是重算一遍。

同理：用户贴给你一段K线数据让你「看看是不是买点」，正确做法是让他给代码、
你去调工具；不要盯着数字硬看。

## 工具

### `chan_analyze` — 单只，看结构

```
chan_analyze(code="600519", levels=["day","30min"], recent=5)
```

- `levels`：`day` / `30min` / `5min`。不确定就先只跑 `day`。
- `zs_from`：中枢建在 `seg`（线段，默认）还是 `bi`（笔）。看大结构用 seg，
  抠小级别买卖点用 bi。
- `recent`：只回最近 N 个中枢和买卖点，默认 5。想看全历史给 `recent: 0`。
- `include_quasi`：是否要「类买卖点」，默认要（见下文）。

### `chan_scan` — 批量，找候选

```
chan_scan(codes=[...], level="day", within=5, kinds=[1,3], sides=["buy"])
```

- 默认**只读本地缓存**，不联网。缓存没有的票会进 `failed`。
- `within`：最后一个买卖点距今不超过几根K线。日线上 5 ≈ 一周。
- 结果多于几十条时，**用 codemode 读 `structuredContent.hits` 自己过滤**，
  不要让人逐条念。摘要里只列前 40 行。
- 扫出来的是**候选**。要下判断，对单只再调 `chan_analyze`。

**一只都没命中时，不要说「这些票上没有买卖点」。** 看 `missed_because`
——它按原因把没中的票分了桶。实测过的一次：391 只扫出 0 命中，其中 97 只的
买卖点就在 5 根K线之内，只是全是 `quasi` 且未确认，被默认条件滤掉了。

| 桶 | 该说什么 |
|---|---|
| `stale` | 有合格的点，只是比 `within` 旧。调大 `within` 就看得到 |
| `quasi` | 最近的点全是**类**买卖点。想看就加 `include_quasi: true`，但要带上它更弱的那句话 |
| `confirmed` | 最近的点都在未完成的笔/段上，被 `confirmed_only` 滤了 |
| `kind` / `side` | 条件卡的，不是市场没有 |
| `none` | 这才是真的「一个点都没划出来」 |

顺带一条反直觉的：`within` 给得很小（几根）同时又要 `confirmed`，在日线上
**近乎自相矛盾**——确认要等这个点之后的笔/段走完，所以几根之内的点在定义上
就还不可能确认。用户要「今天能买的」，给他 quasi/未确认的候选并讲清楚，
比回一句「没有」要诚实。

### `chan_nest` — 区间套，定时机

```
chan_nest(code="600519", levels=["day","30min","5min"], side="buy")
```

用户问「**什么时候**买」「现在还能不能追」这类时机问题时用它；只问结构用
`chan_analyze`。它按 27课 p67 的程序自上而下收缩：日线的买卖点圈出一个时间
窗口，30 分钟在窗口里找同向的点，5 分钟再收一次。

看结果先看两样：

- **`agreement`**：`agree`（各级别一致）/ `conflict`（次级别有反向点）/
  `incomplete`（没能收缩到底）。**不是 `agree` 就不要给确定的时点。**
- **每一层的 `coverage`**：`ok` / `partial`（窗口左段数据缺失）/
  `none`（窗口内根本没有K线）。

`coverage: "none"` 和「这段时间没有买卖点」是**完全不同的两件事**。分钟线
最早到 2020-01-02（C-min），日线窗口比这更早时 30 分钟层必然是 `none`。
这时候说「次级别没有反向信号，可以放心」是彻底错的。

## 数据是哪来的

默认源是 **baostock**，全部 **后复权**。两件事要记住：

- **价位不是现价。** 后复权把基准锚在上市首日，茅台会显示成一万多。这是
  划线需要的口径（不复权的除权缺口会造出假分型）。跟用户说价位时点一句
  「后复权价」，别让人以为是盘口价。
- **跨源不可比。** akshare 和 baostock 的后复权差两成多。输出里的 `source`
  就是干这个用的——不同源的两份结果不要放在一起比价。
- **分钟线最早到 2020-01-02。** 比这更早的日线买卖点，区间套只能停在日线层，
  这时 `coverage` 是 `none`。

还有第三个源 **tencent**，是 baostock 被封、东财限流时顶上去的应急源。它
**只有日线，而且只有最近 640 根（约 2.6 年）**，分钟线和全市场代码表都会直接
报错。看到 `source: "tencent"` 的结果时：

- 不要回答更早年份的问题——**它根本没有那段数据**，不是那段没有信号。
- 不要和另外两个源的价放在一起比（C-src）。
- 区间套在它上面只能停在日线层。
- **北交所（8 / 4 / 920 开头）这个源直接拒绝**，因为它只回当天一根。用户要
  看北交所的票，让他 `--source akshare` 重拉，不要说「这只票没有数据」。

缓存是空的时候工具会报「缓存里没有这只票的K线」。让用户在命令行拉：

```
python -m scan pull 600519 --levels day,30min,5min
```

**拉数据和扫描是两件事，别混。** 扫描只读缓存、秒级；拉取要走网络、
一只票二十秒。工具不会替用户联网补数据，缺了就是缺了（见下面规矩 6）。

## 怎么读输出

### `trend` 是「现在」，不是「这段历史」

`trend` 和 `forward.trend` 是同一个值：**末端那一段还在走的走势类型**，由
级别树切出来（见下面「级别树」一节）。走势类型是时间轴的**划分**，前后两段
以一个点为界、互不重叠，所以「当前这一段」含哪几个中枢是定死的，不是从末枢
往回数出来的。

它不是 17课 p36 的「一个**完成的**走势类型」。那个口径问的是「从第一个中枢
到现在整体算什么」，而一只票几千根K线上必然有一对相邻中枢不同向，于是答案
永远是盘整——实测 15 只票 × 日线/30分/5分**全部**如此。所以你看到
`trend: panzheng` 时，那是真的在盘整，不是口径退化的产物（这个字段以前确实
是，已经修了）。

要说「某某级别是什么走势类型」就用它。`forward.run` 是这一段里有几个中枢：
`run: 1` 是以单个中枢为核心的盘整，`run >= 2` 才是趋势（17课 p36）。

### 级别树（`tree`）：同一串K线自己递归上去的上级别

`tree` 每项是一层：`level: 0` 是本级别，`1` 是上一级，依此类推。每层带
`current`（这一层当下的走势类型 + 起止日期 + 末枢 ZD/ZG）和 `forward`
（这一层自己那张推演表）。`tree[0].forward` 就是顶层的 `forward`，同一份。

**和 `chan_nest` 的 30分/5分不是一回事。** 那套是另外三份K线，受缓存限长
（30分/5分只从 2020 年起）。树是从同一串日线按 17课 p36 一级一级合上去的，
不受这个限制——600000 的上一级能一路追到 2000 年。两套都是「级别」，但一套
是换数据、一套是换读法，说的时候别混成一句。

怎么用：**方向以上层为准，下层定时机**（和下面「三个级别怎么联立」同一条
规矩）。上层说上涨趋势、本级别在中枢里震荡，那就是回调，不是转势。

三条必须守的：

- **上层的背驰经常是「还判不了」，那是没测，不是没背驰。** 上层现在**会**
  测背驰（力度那一行会给出 MACD 面积的具体数），但末枢的离开段还没走出来
  时仍然判不了，那一行会写「还判不了——离开段还没走出来」。两者差着一个
  未知和一个否定：看到「判不了」不许说成「力度还在、趋势没背驰」；看到
  面积数字才可以谈力度。
- **`alt_readings` 出现时每一种读法都要讲**，和 `ambiguous` 同一个待遇。
  它是**当下所在的那一段走势类型**在 33课 p79 多义性下的其余合法答案：
  17课 p36 没规定一串同向中枢必须全并成一个趋势，三个同向中枢就有四种合法
  切法。主口径（`trend` / `forward`）取的是「避繁就简 + 从左往右先定下来」
  那一种，其余的全在这个列表里。只讲一种就是替原文做了选择。
  注意它**只在末段读法真的不同时才出现**（实测 20/60），不出现就是当下这
  一段没有歧义，不必提。
- **`tree_split` 警告出现时，报价位要说清用的是哪一个中枢。** 本级别最后那个
  中枢段数过多（>= 9），树按 33课 p79 把它三等分了：`tree[0].current` 的
  zd/zg 是第三个子中枢（窄），而 `forward` 的触发价和 `zhongshus` 列表用的
  是未拆的那个（宽）。

### ZG/ZD 和 GG/DD 是两回事，别混

| | 是什么 | 谁用它 |
|---|---|---|
| `zd` / `zg` | 中枢**本体**区间，由前三段定死，之后再不变 | **三买比 ZG、三卖比 ZD** |
| `dd` / `gg` | 震荡**包络**，随中枢延伸浮动 | 趋势关系（前后中枢重不重叠） |

混了这两对是最常见的读错。三买的门槛是「回试不跌破 **ZG**」，不是不跌破 GG。

### 可靠性标记，一个都不能略过

- **`confirmed: false`** —— 这个点落在**未完成**的笔或线段上。盘后扫描时
  末端天然如此。它是**线索**，不是已确认信号；后面的K线可能把它整个抹掉。
  跟用户说话时必须讲出来。
- **`quasi: true`** —— 「**类**第一类买点」。它由**盘整**背驰构成，不是趋势
  背驰。原文（第 503 行）说这种点「在小级别中是意义不大的」，要周线以上级别
  才值得看。日线上看到 quasi 的 1买，语气要明显弱于非 quasi 的。
- **`ambiguous: true`** —— 这个三买/三卖落在**原文自相矛盾**的形态上。
  这时候应当明说「这里原文有歧义，两种划法都成立」，并把 `reasons` 里的
  说明转述出去。不要替原文下结论。目前有两种，`reasons` 里会写明是哪种：
  - **C15**：回试段同时是下一个中枢的起手，而新中枢完全不触及原中枢。
  - **C18**：整个形态只用了 4 段——中枢的第三段自己就是离开段。61课 p154
    要求「至少 5 段」，18课 p40 的离开机制又允许 4 段。这种点**明显更弱**：
    围绕中枢的震荡压根没发生过。语气要相应放轻。
- **`macd_law_ok: false`** —— 不符合「1买在 0 轴之下背驰形成」那条 MACD 定律。
  它是**标注不是门槛**（定律依赖 MACD 参数和复权方式，而买卖点的定义是纯
  几何的）。提一句即可，不要据此否掉信号。
- **`level_up: true`**（中枢上）—— 中枢延伸到了 9 段上限，该升一个级别去看
  这一段。可以主动建议用户看周线或更大级别。

### 点的日期，不是它能被看见的日期

一个买卖点标着 `2024-06-28`，**不代表那天收盘能划出它**。中枢要延伸到确认、
回试段要走完，引擎第一次画出来往往是很久以后。走查实测（300308 日线）：

| 类型 | 平均延迟 | 事后能不能站住 |
|---|---|---|
| 1买 / 1卖 | 1 根 | 12 个里只剩 1 个，**绝大多数被后面的K线抹掉** |
| 3卖 | 13 根 | 全部站住 |
| 3买 | **21 根** | 全部站住 |

两头的毛病正好相反，说话时要分开讲：

- **一类点来得快、留不住。** 它几乎总是 `confirmed: false`，当天就看得见，
  但多半活不到下周。别说「出现了1买」，要说「**暂时**划出一个1买，很可能被抹掉」。
- **三类点留得住、来得晚。** 等它稳定地出现在图上时，行情已经走了一大段。
  别拿这个点的日期和价位去讲「当时该怎么做」——那个价位当时没人看得见。

用户拿历史图问「这里为什么不买」时，**先确认那个点在当天是否已经存在**。
详见仓库根目录 `CONVENTIONS.md` 的 C-lag。

### `departed` 是三态，不是两态

`departed: false` **不等于**「价格还在中枢里」。18课 p40 要连续两段都不触及
才算离开，而最后一个中枢后面常常还凑不满两段，于是价格早已跌破 ZD 一大截、
这个标记仍是 `false`。

**自己拿最新收盘价和 `zd`/`zg` 比一下**，别只看标记。读成「仍在震荡」会把
方向说反。详见 C-depart。

### `reasons` 是给你复述的

每个买卖点都带 `reasons`，里面是**带课次和页码的原文依据**。给用户解释时
引用它们，不要自己编一套说法。引擎说「20课 p43 第 966 行」，你就这么说。

## 三类买卖点各是什么

这三类在原文里是**三个完全不同的东西**，不是强度递减的同一种信号：

| | 怎么来的 | 位置 | 出处 |
|---|---|---|---|
| **1买** | 下跌**趋势**背驰 | 最后一个中枢**之下** | 21课 p45 |
| **2买** | 1买之后第二段次级别走势的**结束点** | **任何位置** | 21课 p45 / 第 2203 行 |
| **3买** | 向上离开中枢后**第一次**回试不跌破 ZG | 中枢**之上** | 20课 p43 第 966 行 |

几条容易说错的：

- **2买可以比 1买低。** 原文第 2208 行：「第二类买点跌破第一类买点……
  **这是完全可以的**」。看到 2买 破了 1买 不要说「信号失效」。
- **3买必须是第一次回抽**，不是后面任何一次回调。引擎已经保证了这点。
- **上涨趋势确立之后就不可能再有 1买、2买，只可能有 3买**（21课 p45）。
  所以在 `trend: up` 的票上看到 1买，先怀疑它是不是 `quasi`。
- 2买和3买**可能重合**；1买与2买、1买与3买**不可能重合**（21课 p45 第 363 行）。
  引擎把这条写成了断言，违反会进 `warnings.invariant`——那是划线 bug，
  看到就该告诉用户去报。

## 三个级别怎么联立

27课 p67 的「精确大转折点寻找程序」，**由 `chan_nest` 执行**，你不要自己拼。

它做的是逐级收缩：日线的一个买卖点圈出一段时间窗口 → 30 分钟在这个窗口里
找同向的点，窗口收窄 → 5 分钟再收一次。**每个级别都在自己完整的历史上划线**，
区间套只负责在窗口里挑点，不是把K线切段重划（切段重划是错的：包含处理不
满足传递律，笔和线段还依赖窗口之前的历史）。

读的时候：

- 方向不一致时**以大级别为准，小级别只决定时机**。日线 `trend: down` 而 5 分钟
  出了个三买，那是下跌途中的反弹，不是底——这种时候要明说。
- **但反向的点必须一并报出来。** `steps[].against` 里是窗口内方向相反的买卖点。
  只讲对自己结论有利的那一个，是在替用户隐藏风险。
- `agreement` 是 `incomplete` 时，`precise` 那个时点只收缩到了某一层就断了。
  说「大概在某一天附近」，不要说「就是这个点」。

想看结构而不是时机，就别用 `chan_nest`，用 `chan_analyze`——前者只回每层
一个点，看不到中枢全貌。

## 全市场扫描

几千只用 `chan_scan` 会在中途断掉就全白跑。那种规模让用户在命令行跑三步：

```
python -m scan universe --save all.txt                            # 代码表，约 5200 只
python -m scan pull --file all.txt --progress                     # 日线回填，三四小时
python -m scan fullscan --file all.txt --state run.jsonl --jobs 8 --progress
```

之后每天盘后只要两步——`pull --update`（增量补当天那根）再 `fullscan`。

**只有 `fullscan` 该给 `--jobs`。** 划线是纯 CPU，多进程线性加速；拉数据不是
——baostock 实测并发**只会更慢**（8 进程比串行慢两倍多还掉票），所以 `pull`
的 `--jobs` 会被自动压回 1。别建议用户去调大它。

**分钟线不要全市场拉。** 30 分钟是日线的八倍行数，5 分钟是四十倍，全市场拉
5 分钟是上百小时。正确顺序是先用日线扫出候选，再只给这几十只补：

```
python -m scan pull 600519 601398 --levels 30min,5min
```

两处都可以中断续传，但**靠的是两样东西**：`pull` 靠缓存目录本身（有 CSV
就跳过），`fullscan` 靠 `--state` 那个 JSONL。后者**筛选条件改了会拒绝续传**
——两套条件的结果混在一起看不出来。要换条件就换 `--state` 文件。

首次回填是**几小时**的事，不要在对话里等它。让用户自己在终端跑完再回来。

### 拉取报错时

- **「黑名单用户」** —— baostock 把这个 IP 封了，通常是拉太猛。**不要建议
  重试**，重试只会封得更久。让用户等一段时间，或者 `--source akshare`。但
  换源之后别拿两个源的结果比价（见上面「跨源不可比」）。
- **缓存里的历史起点是 2020-01-01**，和分钟线的起点同一天。用户问更早年份的
  买卖点时，不能说「那时候没有信号」——是**没拉那段数据**。要看就得
  `--start` 单独重拉一份。

## 回答的时候

1. 先调工具，再说话。
2. 说日期和价位，不说K线下标。
3. 每个结论后面挂上引擎给的 `reasons`（带课次页码）。
4. `confirmed: false` / `quasi` / `ambiguous` 必须讲出来，不能为了说得干脆
   而省掉——那会让人以为是确定信号。
5. 原文有歧义的地方，列两种读法，不要硬选一种。
6. **缺数据就说缺数据。** 某个级别没拉到那段历史，不等于那段历史上没有
   信号。把「我看不到」说成「没有」是这里最糟的一种错。

`references/` 里有规则原文摘录和页码，需要核对时自己读：

- `references/rules.md` —— 123 类买卖点、中枢、背驰的原文逐字 + 页码
- 仓库根目录 `CONVENTIONS.md` —— 原文没写死、由实现自己定的规则登记表
  （不在 `references/` 下：它是整个项目共用的，不是这个 skill 的附件）
